# Course IT Style 1

Approved by the user on 2026-10-12 from the 121.4-second USB motion sample.
Preserve the teaching language below, not the USB scenario or its exact timings.
Read [the saved kit](../../../demos/course-it-style-1-kit/README.md) before
implementing; its `style.json` holds the exact design tokens. Discover this entry
with `playbook creative show course-it-style-1@1`.

## Visual explanation

Use the actual system as the actor: devices, connections, components, software
states, diagrams and data. Build one persistent explanatory world per concept.
Keep objects recognizable as their relationships change; retain useful context
and emphasize the current cause, action or result. Use short headlines and one
supporting note rather than turning every sentence into a new bullet slide.

Use navy backgrounds, cream hardware, white teaching text, cyan active paths and
muted inactive context. Use Geist regular/bold, flat geometric silhouettes,
crisp rounded strokes and restrained corner radii. Characters and stick figures
are excluded from this selected style. Keep depth flat and motion purposeful,
without decorative glow, floating panels or constant ambient drift.

## Causal motion

- Assemble or reveal parts as they become relevant in the real narration.
- Draw a connection after its endpoints are established. Move a signal along
  that connection when it explains flow; label schematic movement as illustrative.
- Focus the suspected component without implying an established diagnosis.
- Change the same scene to demonstrate an action. Preserve object identity
  through removal, replacement, bypass or state changes.
- Show controlled comparisons with common conditions. Numerical displays need
  supplied facts or actual measurements; animation is not a benchmark.
- Leave readable holds. A quiet diagram can be the correct picture while the
  speaker explains it. Use the token file's durations as starting ranges,
  adapting to the actual speech rather than stretching a fixed loop.

The USB example demonstrates symptom → inspect the path → testable theory →
safe action → simplify → compare → interpret. This is an available troubleshooting
structure, not a compulsory sequence for definitions, architecture or procedures.
For networking, show relevant endpoints and packet routes; for memory, use
components and state; for installation, use dependencies and checkpoints. Design
new geometry and labels for the topic rather than relabeling a USB hub blindly.

## Adapt and verify

For supplied footage/audio, reuse or prepare evidence with the editor's normal
agent workflow. Establish the course claims, objects, relationships, narration
cues, reading time and any protected presenter regions before authoring. Local
ASR is fallible: verify terminology and units against the supplied script/source.
Bind reveals to the new narration, not this example's 121.4-second timeline.

The saved implementation is a landscape full-frame SVG/HTML + GSAP authoring
example for HyperFrames, not a native motion-catalog recipe, automatic importer,
universal generator, transparent overlay or verified Remotion/portrait adapter.
Use the installed HyperFrames workflow/core/motion skills for that renderer.
Another renderer or a camera/vertical layout needs its own implementation and
review. Use original narration when supplied; this style does not require a
cloud model, generated voice, stock footage or background music.

On each adaptation, inspect actual entrance/hold/exit frames and relevant flowing
states; check text safe zones, units, causal ordering and direct/backward seeking.
For stroke-dash motion, inspect painted pixels rather than only bounding boxes.
Check audio timing and report listening coverage honestly. Present the new
preview for approval before delivery under the active workflow. Approval of this
style is not approval of future content, exports or publishing. Existing vlog
preferences and other styles stay unchanged.
